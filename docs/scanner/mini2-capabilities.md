# Revopoint MINI 2: capability map and allow-list proposal (research, 2026-11-18, hardware not touched)

Evidence tags: **M2** measured on our MINI 2 · **M1** Revopoint MINI 1 over WiFi (fw 7.6.9, HazenBabcock) · **P4** POP4 over USB (All3DScan) · **P3** POP3 (TamedTornado) · **I2** Inspire 2 · **SDK** public 3DCamera SDK v3.2.229 headers/CHM docs · **APK** static analysis of Revo Scan 6 Android (All3DScan notes, second hand). Risk: **R0** standard UVC/V4L2 · **R1** XU read-only · **R2** XU file-channel read (a SET to open the file) · **R3** volatile register write via the shell channel (sel 7) · **R4** can alter firmware, calibration or identity: never.

## Bottom line (read this first)
1. **Frame period = 18 patterns x per-pattern frame time.** SDK FAQ 2.4: "frame time x 18", e.g. 5 ms gives about 11 fps. Our 365 ms / 18 = **20.3 ms per pattern**. M1 showed the same ~20 ms floor, flat from 0.8 to 12 ms exposure, over 12 patterns (12 x 20 ms = 240 ms = 4.2 fps). Bright scenes reach 5.2 ms (10.7 fps), so the device auto-exposure (AE) already stretches frame time with scene darkness. [inference, medium] 2.74 fps is the AE ceiling in the dark, not a hardware limit. The levers are `0x912` (AE mode), `0x910` (frame time), `0x911` (exposure), `0xa05` (fringe pattern 6 = "high speed", 2 depth frames per cycle), probably how Revo Scan reaches "up to 16 fps". Nobody has tried `0x910` or `0xa05` on a MINI.
2. **The factory calibration is stored on the device and can be read over the XU file channel** (P4, verified; `camparam.yaml`, `Pl.bin`, `Q.bin`, `Distort.bin`). Not yet tried on a MINI 2. It would replace fx=fy=1190 with real values. One-time session, R2.
3. **Depth unit**: SDK Z16 is `mm = raw x depthScale`, a linear pinhole `x=(u-cx)z/fx` with no distortion term. 0.005 (= our 1/200) is one of the SDK's fallback scales (APK), which is circumstantial support. The real value is `1/divisor` from property `0x918`. The USB framing for that read is unknown. A host-only check is possible once calibration is read (see 3).
4. Our `calib.rs` doc says a vendor `camparam.yaml` "can be used as is". The vendor file holds OpenCV matrices (`cameraMatrixL: !!opencv-matrix ... data: [..]`, `width: "960"`), not `fx:` lines. From reading the code (not run), the parser needs a small OpenCV-matrix reader, and `Pl.bin` is raw f32. Fix this before the calibration session.

## What the numbers mean for scan quality
- Fixed frame time gives a steady cadence and a fast device-timestamp-to-host path. The header timestamp (bytes 20-23, ms) is the right fps metric. Use it, not host arrival time.
- M1 warning: at exposure <= ~10 ms, depth coverage came in pairs of good then bad frames (projector about half brightness on bad frames). Gate frames by valid-pixel count against the running median before tracking.
- SDK rules: gain 1-16, keep <= 3 for accuracy (register `0x903` = 16*g; V4L2 gain is already allowed). Exposure 3000-60000 us range string in the header comment (that is the SDK doc, not measured on MINI 2). Exposure must be <= frame time. The vendor viewer sets frame time = exposure + 2000 us first, then exposure. P3 range was 5000-65000 us.
- Header row word 4 (0x160 -> 0x148) varies between sessions. It might be a frame-time or exposure echo. Cheap read-only test: log it next to the measured period and the lighting. [speculation]
- Revo Scan UI mapping (MINI 2 guide, RS5 guide): Accuracy Standard/High (host post-processing), High-speed (faster fps, per-model), Tracking Feature/Marker, Object type General/Dark (Face/Body/Large only some models), Depth exposure auto or slider (blue = under, red = over), RGB exposure plus white LED toggle. Scanner buttons: Exposure -/+ and Start/Pause. "Up to 16 fps" is Revopoint's claim. Spec WD 120-250 mm, 168x132 mm at 250 mm, 52x64 mm at 120 mm.
- Revo Scan 5 cache `.dph` frames are **disparity-like** and need `Q.bin`: `Z = Q[2,3]/(d*Q[3,2]+Q[3,3])` (device unknown, probably POP-class). That is not our USB Z16 (linear, grows with distance, M2). Do not mix the two models.

## Candidate allow-list (exact match, no composition; anything else is refused)
**T1 approve now (R0/R1):**
- V4L2: `ENUM_FMT`, `ENUM_FRAMESIZES`, `ENUM_FRAMEINTERVALS`, `QUERYCTRL`, `G_CTRL`; `S_CTRL` brightness and gain (already allowed).
- `UVCIOC_CTRL_QUERY` on unit 4: GET_INFO, GET_LEN, GET_MIN, GET_MAX, GET_DEF for sel 1-8, 10, 14; GET_CUR only for sel 3 and sel 6.
**T2 one supervised session, device idle, before streaming (R2):**
- File read, opcode byte `0x01` only, 60 B frames. Close with the zero frame. At most one retry, abort on any error (P4: after a session the channel answered `LIBUSB_ERROR_IO`, and a ~40 s USB reset fixed it). Read cap 64 KiB. Paths:
  `/data/camparam/camparam.yaml`, `/data/camparam/Pl.bin`, `/data/camparam/Distort.bin`, `/data/camparam/camparamLR/Q.bin`, `/data/camparam/LC_RT.bin`, `/data/camparam/Prgb.bin`, `/data/camparam/mapparamL.bin`, `/data/camparam/mapparamR.bin`. If a path is empty, also try `/userdata/camparam/` (APK hint). Optional: `/tmp/inited` (firmware version string, M1).
- Save the raw bytes untouched to the dataset folder first; parse afterwards.
**T3 supervised experiments, volatile, each with before/after metrics and an abort rule (R3).** Transport: sel 7, ASCII, NUL-padded to 60 B, regex `^echo s 0x(b02|b03|b12|910|911|912|a05) [0-9]{1,5} >/dev/rk_preisp$`:
- Fill light (already authorised): `echo s 0xb03 1 >/dev/rk_preisp`, `echo s 0xb02 1 >/dev/rk_preisp`, `echo s 0xb03 0 >/dev/rk_preisp`.
- Fill level: `0xb12` in 0..255 (test 60, 128, 255).
- Speed: `0x912` in {0, 1} only, `0x910` in 5000..20000, `0x911` in 3000..20000 with exposure <= frame time - 2000. Order: 0x912, then 0x910, then 0x911. Leave >= 6 frames or 2 s between any two writes of the same register (P4 stall). Sweep 20000 -> 12000 -> 8000 -> 6000 and stop at the first drop in valid pixels (> 30% vs the 20 ms baseline) or any missed frames. The escape hatch is a physical replug (assumed, not verified, that these registers are volatile).
- Pattern: `0xa05` in {0, 6} only, after the speed tests, stream stopped and restarted around it.
**T4 never (R4 or known to hurt):** sel 1 with any opcode but `0x01`; sel 4, 5, 10 writes (P4: dropped the composite device); `0x914`; `0xb00`, `0xb01`, `0xb04`, `0x48d`, `0x3001`, `0x3010` (laser-line modes; leaving them needs a ~40 s reboot); `0x702`, `0x904`, `0x903`; every SDK property `0x22` param-file management, `0x6` serial, `0x7` MAC, `setUserData`, `hidUploadFile`/`hidLoadFile`, `startIMUCalibration`, `setIMUCalibrationDate`, `PROPERTY_EXT_EXECUTE_CMD (0xffff)` with free text, `setlaserCalParam`, firmware upgrade (`Upgrade.h`), remount; every HID write. Never let Revo Scan run a "Calibration" on this unit: per Revopoint it resets the scanner's internal parameters, i.e. overwrites the factory file.

## Uncertainties and gaps
- Everything under R3 is inferred from other models. I2 shows the same registers collapsing the laser on a sibling, P4 shows stalls, M1 shows they work. Treat MINI 2 as unknown. [confidence: medium for the fps theory, low for each register's exact effect on MINI 2]
- MINI 2 file paths and calibration resolution are not documented. Camparam on P4 is 1280x1024 native, POP3 1280x800. Scale intrinsics by stream width / calibration width, per SDK `generatePoints`. Our 800x600 depth is already rectified, so use `Pl.bin` / `pL`, not `cameraMatrixL`, for the pinhole.
- Shell channel is write-only (GET_CUR returns zeros; P4). Effects are visible only in frames and the header. The shell is a real shell; hence exact-match lines only.
- No source documents the real MINI 2 UVC frame intervals. 16 fps is marketing. The depth scale of `0.005` as the MINI 2 value is circumstantial.
- Licence: the SDK headers are mirrored under the Chishine3D licence (no use with non-Chishine cameras, no decompiling). I used only register and enum numbers as interface facts and copied no code. All3DScan removed Windows-app-derived findings at the owner's request; I did not open the Revo Scan installer in `tmp/`.
- VM USB passthrough hung this firmware once (see skill). Do the calibration read on bare metal, once.
